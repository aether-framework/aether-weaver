Reports an @Extension declaration the build is going to refuse, on grounds the source alone settles.

This inspection matters more than its neighbours, and for a reason worth knowing. An extension is validated once: by the time anything is woven, javac has already compiled every caller against a compile-time stub derived from the declaration. A declaration that turns out to be wrong is wrong in code that already exists — so finding out while typing it, rather than after writing fifty call sites, is the difference between an edit and a migration.

  • AW1300 — the extension class is not final; it is never instantiated and never subclassed
  • AW1301 — a public method is not static; the receiver arrives as a parameter, so there is no instance for it to be called on
  • AW1302 — a contributed method names no receiver, so nothing says what type it is contributed to. @Receiver on the first parameter contributes an instance method; @Receiver(Type.class) on the method contributes a static one. A method that is not part of the contributed surface belongs in the class as a private helper
  • AW1303 — @Receiver is not on the first parameter. The rewrite passes the receiver straight through as argument zero, which is where the JVM has already put it for the virtual call
  • AW1304 — the receiver is a primitive, an array or a type variable, none of which can carry a method for javac to resolve against — or a @Receiver on a method named no type at all, which leaves it at its default of void
  • AW1305 — the receiver already has that exact signature, declared or inherited. javac resolves to the real member, so the extension would never be reached
  • AW1306 — the extension class is generic; a type parameter on the holder has nothing to bind to at the call site
  • AW1307 — the extension class has a superclass or an interface, stating a relationship nothing at the call site can honour
  • AW1308 — the class contributes the same call twice. Two contributions collide on name and descriptor, so ordinary overloads are two calls and not one; two methods with a single erased signature do not compile, which means one class cannot reach this in valid Java. The build reports it where it does happen — when two separate extension classes contribute the same call
  • AW1310 — a contributed method declares its own type parameters; the stub would carry a type variable with nothing to bind it
  • AW1311 — the receiver is a parameterised type. Erasure is all a call site has, so @Receiver List<String> would be contributed to every List in the program
  • AW1312 — the receiver is java.lang.Object, so the method is offered on every expression in every module that reads the extension. A warning rather than a refusal: it is occasionally what somebody means, and far more often the widest type that happened to compile
  • AW1313 — a receiver is named on the method and on a parameter. The two forms describe different methods — a static member of a type, and an instance member of its values — and a declaration asking for both says nowhere which it is

AW1305 is the one to reach for the API documentation about rather than work around. An extension cannot override, intercept or shadow anything: to change what an existing method does, use @Weave with @Inject or @Redirect, which are built for that and say so at the declaration.

Four of these carry a quick fix, and they are the four with one mechanical repair and no judgement in it: declare the class final (AW1300), declare the method static (AW1301), mark the first parameter @Receiver (AW1302, offered only where the parameter's type could carry a method at all), and move the @Receiver parameter to the front (AW1303).

The rest are offered none on purpose. What a primitive receiver should become, what to rename a method that collides with a real one, how a generic extension should be narrowed — each is a design decision, and a menu entry guessing at it would produce compiling source that means something the author did not choose.

Deliberately absent is AW1309 — the receiver having since grown the method. That is a statement about a class file at weave time, possibly against a different JDK from the one open in the editor, and the editor has no way to know which. The build reports it where the class file is actually in hand.
